## URD-046 — A letter lesson's one unavoidable confusable pair always collides identically, every round
attempts: 0
files: src/exercises/generator.ts
definition of done: `separateConfusables` (URD-022) spreads visually
  confusable letters apart within a lesson's rounds, but the round-major
  loop reuses one fixed order every round, so wherever a bucket forces one
  residual adjacency (only `l-3`'s 4-letter `re` family — a bucket exactly
  `ceil(groupSize/2)` — real corpus today), it is the identical pair,
  `zhe` then `re`, at all 5 of the lesson's round transitions, not a
  varied one. Reinforcing the exact same two letters back to back five
  times is a worse version of the risk this item names ("teaching the
  confusion") than hitting five different pairs once each would be. Vary
  which specific bucket member sits at each end of the round across
  rounds — without changing which letter has which stable index, since
  `turn`/`position` below are computed from a letter's own index plus the
  round number and only cycle correctly if that index never moves (see
  `separateConfusables`'s own doc comment, and the multi-round history two
  functions below it, for what breaks if a letter's index depends on the
  round) — so a learner who does see the forced collision sees a different
  pair of the family each time, not one pair five times over.
verify: a test asserting that across a lesson's round transitions, no two
  round-boundary confusable-pair occurrences involve the identical two
  specific letters twice, for every real letter lesson where a forced
  adjacency exists.
notes: Found designing URD-022's fix. Not blocking — URD-022 itself already
  reduced `l-3`'s confusable-adjacent count from 30 (5 pairs internal to
  every one of 6 rounds, under the pre-fix raw ordering) to 5 (the same one
  pair, once per round transition), a real, measured improvement; this is
  a further refinement to *which* pair recurs, not whether one does.

  RESOLVED. Re-measured the real count first rather than trusting the
  item's own "5 occurrences" figure: URD-043's later letter-major tail
  restructuring (shipped after this item was filed) had already changed
  the count to 4 without anyone updating the comment — a live example of
  exactly the stale-assumption risk this codebase's own history warns
  about, caught before it could propagate into this fix's own reasoning.

  `separateConfusables` now takes an optional `rotation` parameter
  (default 0, so every existing caller — including the one call this
  function already had — is unaffected). It rotates each confusable
  bucket's own member order before slotting members into that bucket's
  *same fixed position-set* (`{0,2,4,6}` for the largest bucket, `{1,3,5}`
  for the next, and so on) — varying which specific letter ends up at the
  array's two endpoints (and so, which letter's exercise is adjacent to
  the next round's first) without ever touching *which positions* a
  bucket occupies, so the "zero internal adjacency" property URD-022
  established is completely untouched.

  The round-major generation loop calls `separateConfusables(groupLetters,
  round)` for each round's own *visiting order*. Critically, every
  letter's `turn`/`position` index is looked up from a separate, single,
  permanent, unrotated map (`idxOf`, built once from `separateConfusables
  (groupLetters)` with no rotation) — never from where a letter happens to
  land in a given round's rotated visiting order. This is what makes the
  fix safe: the item's own notes had previously rejected varying the order
  at all, reasoning that any reordering would have to double as the
  letter's permanent identity index and so reopen the kind-repetition/
  sibling-collision bugs this file's history had already fought through
  several rounds to fix. That rejection held only because it conflated
  two things that don't have to be the same call — "which order are
  letters emitted in this round" (now varies) and "what is this letter's
  permanent id for turn/position purposes" (stays exactly as before).

  **First rotation formula tried and rejected by direct measurement, not
  assumed correct.** Rotating by `rotation % bucket.length` stopped the
  wrap from showing the identical pair every time, but real measurement
  showed it only ever alternated between two pairs (`{Re,zhe}`/`{re,ze}`),
  each still twice over `l-3`'s four wrap transitions. Real structural
  cause, not a fluke: comparing a round's *last* slot to the next round's
  *first* slot is always exactly two rotation-steps apart, and for a
  4-member (even-sized) bucket, any rotation step coprime with the bucket
  size still lands on an even bucket-index distance — which for a 4-member
  bucket only ever reaches two of its possible edges. Fixed by rotating
  with period `bucket.length - 1` instead of `bucket.length` — one
  shorter than the bucket itself breaks that resonance. Checked directly
  against `l-3`'s real 42-exercise output: all four wrap transitions now
  land on four genuinely distinct unordered pairs (`{Re,zhe}`, `{re,ze}`,
  `{Re,re}`, `{re,zhe}` as currently measured — the test re-measures this
  live rather than hardcoding it, so it can't go stale).

  **THE CRITIC** (real generator logic — exactly the "did the fix actually
  work, or does it just look like it did" class of claim this codebase has
  been burned by before). No BLOCKING, no MAJOR. Independently re-derived
  the entire claim from the real generated output rather than trusting the
  diff: dumped every letter's `(kind, position)` sequence across all 9
  real letter lessons, old commit vs. new, and confirmed byte-for-byte
  identical except for `l-3`'s own emission order (first divergence at the
  first rotated round, exactly as expected) — directly proving
  `turn`/`position`/kind stability, not merely accepting the doc comment's
  claim of it. Mutated the fix twice (no rotation; the naive `%
  bucket.length` modulus) and confirmed the new test fails both ways with
  precisely the shape the doc comments predict. One MINOR, fixed: a
  redundant trailing `% bucket.length` in the offset computation that
  could never actually change the result (`period` is already `<=
  bucket.length` by construction) — removed, with a comment recording why
  it was dead rather than load-bearing, so a future reader doesn't assume
  it was guarding a real case.

  **CURRICULUM CRITIC.** No BLOCKING, no MAJOR. Independently measured all
  9 letter lessons and confirmed `l-3` is the only one with any forced
  adjacency at all, that the 4 realized pairs are genuinely distinct (not
  the rejected 2-pairs-twice intermediate), and that varying the pair
  (rather than concentrating repetition on one) matches both this app's
  own stated design philosophy (URD-022's own definition of done: "risks
  teaching the confusion rather than resolving it") and the general
  interleaving-vs-blocking literature on category learning — found no
  curriculum argument favoring the old, unvaried design. Also confirmed
  this correctly leaves URD-047's own separate gap (a dedicated
  discrimination exercise kind, "tell apart" rather than "keep apart")
  untouched — this item only varies *which* letters get kept apart from
  each other, never whether any are ever asked to be told apart. One
  MINOR, fixed: a doc-comment's illustrative example pair (`{zhe,ze}`)
  did not match the real measured pairs — corrected to the actual measured
  set.

  Every fix verified as a real regression its own test catches: reverted
  the rotation entirely (reproduced the original bug exactly), then tried
  the naive `% bucket.length` modulus (reproduced the 2-pairs-twice
  intermediate exactly), then restored and reconfirmed clean.
