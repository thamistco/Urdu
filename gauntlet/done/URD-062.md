## URD-062 — a base letter's note names its own shape, not the mark that separates it from its variants
attempts: 0
files: src/data/letters.ts
definition of done: every confusable bucket is one base letter
  (`confusableWith` unset) plus its variants, and the curated notes were
  written to that shape: a variant's note contrasts it against its base
  ("Daal with one dot above", "Kaaf with a second stroke on top"), while a
  base's describes it standing alone ("A soft angled stroke...", "Three
  teeth..."). URD-047's contrast exercise reveals a note after answering, and
  for the 13 base letters that note does not name the distinguishing mark.
  Two are worse than unhelpful when read after a wrong answer: `kaaf`'s "The
  stroke on top is part of the letter, not an accent. Do not drop it." is
  read by a learner who just wrongly tapped `gaaf` — which is kaaf with a
  *second* stroke on top — as endorsing what they picked; `seen`'s "Three
  teeth" is equally true of `sheen`, the letter they confused it with. Give
  each base letter's note a clause naming what its variants add and it does
  not have.
verify: a test asserting every base letter in a multi-member bucket has a
  note whose first sentence names the distinguishing mark (a dot, a stroke, a
  madda) or explicitly its absence.
notes: Found by THE CRITIC and CURRICULUM CRITIC independently while
  reviewing URD-047. URD-047 mitigated the wrong-answer case in code without
  touching content — `contrastNotesFor` shows the tapped letter's line
  alongside the target's, and since a bucket holds exactly one base, any
  wrong answer necessarily involves a variant whose line IS contrastive. What
  that cannot reach is the base letter's own correct-answer panel, where "no
  dot" is precisely the thing worth saying and nothing says it. That needs
  content, which is why it is filed rather than fixed.

RESOLVED. All 13 base letters' `note` fields (`letters.ts`) edited so their
first sentence — the only part `contrastLine` (`letterContrastNotes.ts`)
ever shows in the post-answer panel — names the mark that separates the
base from its variant(s), or explicitly its absence: `alif` (no madda),
`be` (one dot, not pe's three), `jeem` (one dot, not che's three),
`baRi-he` (dotless, khe adds one), `daal` (no dot, no retroflex mark),
`re` (no dots, no retroflex mark), `seen` (no dots, sheen has three),
`swaad` (no dot, zwaad has one), `toe` (no dot, zoe has one), `ain` (no
dot, ghain has one), `kaaf` (one stroke, gaaf adds a second), `noon` (one
dot, noon-ghunna has none), `choti-ye` (a small hooked tail, not
baRi-ye's long sweeping one).

Dispatched both THE CRITIC and CURRICULUM CRITIC via the WIP-commit
review pattern (reset after both reported). Both found a real defect the
first version missed.

**CURRICULUM CRITIC (MAJOR, fixed): `choti-ye`'s original clause named an
invisible fact.** The first draft read "joining within a word rather than
baRi-ye's wide tail at the end of one" — a true fact about `connects:
true` vs `false`, but `LetterContrastExercise` (`LetterExercises.tsx`)
renders only `forms.isolated` for every option tile, never a word or
joined form. A learner staring at two static, unconnected glyphs (`ی` vs
`ے`) reading about "joining within a word" is being told something they
cannot see in front of them — the one clause in the batch that failed
the job the item exists for, unlike the other 12, which each describe a
mark literally visible on the isolated glyph. Fixed by naming the actual
visible difference instead (tail shape), mirroring the language
`baRi-ye`'s own untouched note already uses ("a wide sweeping tail").

**THE CRITIC (MAJOR, fixed): the first version's test table was
keyword-gameable, proven by mutation.** A loose `/dot|retroflex/i`-style
regex per base only proves a keyword is present, not that it correctly
names the real mark — reproduced live: rewriting `daal`'s note to mention
"a single dot of ink where the pen first touches the page" (true of
nothing about `Daal`/`zaal`) still passed every test. Fixed by tightening
the check itself, not just the content: the 11 single-variant buckets now
require that variant's own id to appear by name (word-boundary matched;
nothing else in the corpus is named "gaaf" or "zwaad", so this can't be
gamed the way a bare "dot" check could), the one bucket where naming the
variant by its literal data id would be unnatural prose (`alif`/
`alif-madda`) instead requires "madda", a specific diacritic name rather
than a generic word, and the two multi-variant buckets (`daal`: `Daal`/
`zaal`; `re`: `Re`/`ze`/`zhe`) now require *both* "dot" and "retroflex" to
appear, not either, since a bucket that size can only be honestly
described as lacking both. Re-verified against THE CRITIC's own exact
repro (the mutated `daal` note above): the tightened test now fails it
correctly, on the retroflex-absence assertion specifically.

THE CRITIC's separate MINOR (the test reimplemented `contrastLine`'s
split logic instead of importing and calling it) fixed in the same pass —
the test now imports `contrastLine` directly, so a future change to its
split behavior is exercised by this test rather than silently diverging
from it.

**A third defect, caught by `check:writing` (not by either critic) when
running the full gate before the final commit: 8 of the 13 new clauses
used an em dash, and one (`noon`) spelled a variant's hyphenated data id
(`noon-ghunna`) directly into prose.** House style forbids any dash in
user-facing copy, `note` included — neither critic's review scope
happened to run this specific check, and I hadn't run it myself before
dispatching either. Fixed by rewriting each em-dash clause with the
punctuation the sentence actually needed (mostly a semicolon), and by
referring to `noon-ghunna` and `baRi-ye` in prose by their space-separated
`name` field (`noon ghunna`, `baṛī ye`) instead of their hyphenated `id`,
matching the convention the corpus's own untouched notes already use for
`choṭī he`. The test's `NAMES_VARIANT` table updated to match (its keys,
which are the base letters' own ids, are unaffected — only the two
prose-name values changed). Re-verified: `node scripts/check-writing.js`
clean, and the full test suite still 273/273 after the rewrite.

Also independently re-verified, before treating either critic's finding as real:
`LetterContrastExercise`'s render call (`o.forms.isolated`, confirming
CURRICULUM CRITIC's premise), and THE CRITIC's `daal`-mutation repro
against both the original loose regex (passed, wrongly) and the
tightened check (fails, correctly).

Everything else both critics checked came back clean: the 13-bucket
count and every other clause's factual accuracy (verified against each
letter's real `forms` and its variant's own note), the `kaaf`/`seen`
fixes reading correctly in the exact wrong-answer moment they were
written for, quote/apostrophe hygiene (curly quotes and em dashes
throughout, matching the file's existing convention), no truncation or
corruption of any note's remaining text, and `letterContrastNotes.test.ts`'s
own guarantees (which operate on bucket shape and variant notes only,
never base-note content, so structurally unaffected by this diff).
