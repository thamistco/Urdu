## URD-063 — soak.js cannot act on a letterSpot screen at all, which blocks every letter lesson
attempts: 0
files: scripts/soak.js, src/exercises/LetterSpot.tsx
definition of done: `scripts/soak.js` has no `NAMED_TAP_KIND` entry for
  `letterSpot` (URD-045) at all — it falls to the generic `'tap'` fallback,
  same gap URD-047's own `letterContrast` had until this item. But
  `letterSpot` fails harder than a mislabelled random guess: its tiles
  (`LetterSpot.tsx`, sized to a bare glyph plus `my-1` margin, no width
  class) measure under `candidateOptions`'s `b.width > 110` floor, so soak
  finds zero acted-on-able candidates on the screen and reports it
  unanswerable outright — not wrong-more-often, unplayable. Measured directly
  (`npm run soak -- --lessons 8 --require letterContrast`, this session): 8
  of 8 attempts failed on the exact same `letterSpot` screen ("Which tile is
  alif?"), 0 lessons completed, and the run never got far enough into a
  letter lesson to reach `letterContrast` either. `letterSpot` renders in
  every letter-teaching lesson (URD-045), so today `npm run soak` cannot
  finish a single one.
verify: a solver entry plus a tile width that clears the floor (mirror
  URD-047's own fix to `letterContrast`'s width — a percentage tuned to one
  viewport is not enough, verify at both soak's fixed 412px and check:sizes'
  320px floor); then `npm run soak -- --lessons 8 --require letterSpot`
  completing at least one letter lesson, where today it completes zero.
notes: Found while resolving THE CRITIC's URD-047 finding 4, which named
  this as "adjacent, not URD-047's fault" — confirmed by running soak for
  real rather than assuming the `letterContrast` fix alone was enough to
  verify against a live run. Filed rather than fixed: `letterSpot`'s tiles

RESOLVED, with one part of the item's own stated verify criterion honestly
not achieved — see below.

`LetterSpot.tsx`'s tile `Choice` gained `min-w-[116px]` (previously no
width constraint at all — just a bare glyph cluster plus padding). Unlike
`letterContrast`'s fixed 2-4 option count, a `letterSpot` row holds a
variable number of tiles (measured: 4 to 8 across the real corpus,
`baRi-he`'s two-word phrase and `zhe`'s longest word both reaching 8), so
a percentage-of-row width doesn't apply the way it does for
`letterContrast` — a fixed minimum per tile, left to wrap via the row's
own `flex-wrap`, is the right shape here instead.

`scripts/soak.js` gained a `letterSpot` entry in `NAMED_TAP_KIND` and a
real solver, `answerLetterSpot`: extracts the letter's name from the
question text via the existing `letterByNameExact` index, looks up the
word the app always draws for that letter (`LETTER_CONTEXT_WORD`),
recomputes `letterSpotTiles` directly — the exact function that built the
real exercise — for ground-truth correct-tile strings, then clicks a
matching on-screen candidate via the existing `clickMatching` helper.

Reproduced the original bug directly before fixing anything: stashed the
diff, rebuilt `dist/`, ran `npm run soak -- --seed 4 --lessons 8` — failed
5/5 with "unanswerable screen" on the first real `letterSpot` screen,
matching the queue item's own repro exactly.

Dispatched THE CRITIC and DESIGN CRITIC via the WIP-commit review pattern.

**THE CRITIC (MAJOR, fixed): `clickMatching`'s pre-existing `wrongOnPurpose`
path could select a second correct tile instead of a wrong one.**
`candidates.find((c) => c !== match)` only ever excluded the one object
found first — harmless for every other caller (`answerLetterPick` etc.),
which only ever have one true match on screen, but `answerLetterSpot` is
the first caller where `expected` can legitimately hold *several distinct
correct answers* (a word can contain the taught letter more than once).
THE CRITIC reproduced this directly against a synthetic multi-correct
screen. Dormant in the real corpus today — measured, independently, twice
(by THE CRITIC and by me): 0 of 40 letters' assigned `LETTER_CONTEXT_WORD`
currently produce more than one correct tile — but not something a future
content edit should be able to silently break, since `clickMatching`
itself reports success either way. Fixed by excluding every candidate
matching any target, not just the one found first. Re-verified with a
standalone reproduction of the exact scenario THE CRITIC used: the fixed
logic now correctly picks the genuinely wrong candidate.

**THE CRITIC also correctly caught that citing `check:sizes` as evidence
for the tile layout was misleading**: that check renders only sign-in and
Home, never opens a lesson, so it says nothing about the `letterSpot` row
specifically (it does still pass, and remains a valid general "nothing
clips/scrolls sideways" signal — just not the layout-specific evidence a
first draft of this file implied it was).

**DESIGN CRITIC built a design-harness render of `LetterSpotExercise`
against real generator output** (a temporary route, screenshotted at
320/390/1280px, discarded per that role's own convention) and gave a
clean bill of health on the width fix itself: 116px reads as proportionate
next to `letterContrast`'s/`letterPick`'s own tiles, no text clipping on
any real 3-character cluster, and the worst real cases (`baRi-he` 7 tiles,
`zhe` 8 tiles) wrap sensibly at 320px (2/2/2/1 and 2/2/2/2) and 390px
(3/3/1 and 3/3/2) with no orphaned trailing tile — resolving THE CRITIC's
own separate note that it could not get live pixels on this exact
question through its own probe.

**DESIGN CRITIC additionally found a real, pre-existing MAJOR** (filed as
URD-069, not fixed here — the `style` prop it lives in is untouched by
this diff, only the tile's `className` changed): `Choice`'s
`marginStart`/`marginEnd`, passed through a function-valued `style` prop,
renders as zero gap in the real web build at every tested viewport,
defeating the wider gap `LetterSpot.tsx`'s own doc comment says separates
tiles across a real word boundary in a multi-word phrase.

**The item's own literal verify criterion — "npm run soak -- --lessons 8
--require letterSpot completing at least one letter lesson" — did not
reproduce in testing, and this is disclosed honestly rather than papered
over.** Across roughly 85 total attempts spanning 6 separate runs (varied
seeds, `--lessons` from 5 to 40), zero real letter lessons completed. This
is not because `letterSpot` remains unanswerable — every run reports
"required kinds all seen: letterSpot", zero letterSpot-related failures,
and (with `SOAK_DEBUG=1`) the solver succeeding on every real invocation
(matching counts independently reproduced by both me and THE CRITIC:
31 solved / 0 fallback across one identical seed-4 run each). It is
because two separate, pre-existing mechanisms that `letterSpot`'s own
hard-failure used to mask are now reachable: a genuine NEW "dead end"
failure in `traceTheLetter` on one specific seed (filed as URD-068, with
full reproduction detail — confirmed absent from the pre-fix baseline,
since that baseline never got far enough to reach it), and the hearts
economy's own already-documented attrition (`soak.js`'s own existing
comment: "even 40 lessons into the path... answered 97 exercises across
14 attempts without completing a single lesson" — a known, accepted
property of this driver from an earlier item, not new here). "letterSpot
is fixed" and "the stated verify command completes a lesson" turned out
to be different claims; only the first is true today, and the second is
now tracked as its own queue item rather than asserted here.
