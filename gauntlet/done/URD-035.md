## URD-035 — A grammar teaching card can crash to a blank screen
attempts: 1
files: src/exercises/GrammarExercises.tsx
definition of done: `GrammarTeachExercise` throws an uncaught
  `TypeError: Cannot read properties of undefined (reading 'N')` (N varies:
  observed 0, 1, 2, 3 across runs) partway through its reveal-a-stage flow
  ("Show the pattern" → "Show examples" → "Got it"), reproduced on two
  independent grammar concepts and seeds. The error is not caught by any
  boundary — the screen goes blank (empty `document.body.innerText`) and
  the app does not recover on its own. A test or a driver run should never
  see this; a real learner tapping through a teaching card at ordinary
  speed could.
verify: npm run soak -- --start 29 --lessons 3 --seed 7 --require grammarTeach
  reports 0 failures (today it reports an uncaught error and a blank
  "unanswerable" screen every attempt).
notes: Found chasing down THE CRITIC's BLOCKING finding on URD-005 (that
  `reading`/`dialogue`/`grammarTeach` couldn't be named by `--require`,
  which turned out to be hiding this — those screens use `<Button>`, not
  `<Choice>`, so they were never actually being exercised at all before
  this session, by `--require` or otherwise). Confirmed real and
  reproducible: identical crash shape on `g-pronouns` (seed 7, `--start 29`)
  and `g-gender` (seed 11, `--start 45`); ruled out a driver-timing race
  first (added a 200ms settle wait after each reveal tap — no change).
  Screenshots in `.soak/` from the reproducing runs show the blank result
  directly. Root cause not diagnosed past this point — likely an array
  index into `concept.table` or `concept.examples` going out of bounds
  during the stage-reveal sequence, but that needs someone reading
  `GrammarExercises.tsx`'s `stages`/`shown` logic against real `GRAMMAR`
  concept data, not more soak driving.

  Third independent reproduction found while shipping URD-034 (`--start
  200 --track roman --seed 55`): same alternating "unanswerable
  screen"/`TypeError: Cannot read properties of undefined (reading 'N')`
  shape on `grammarTeach`, confirmed independent of URD-034's own driver
  changes by re-running with its new grammarDrill solver forced back off
  — identical failure either way.

  RESOLVED, and the item's own diagnosis was wrong about which component
  crashes — worth stating plainly rather than quietly correcting, since it
  is exactly the "verify, don't assume" mistake this project's own CLAUDE.md
  names first. Every prior note above blamed `GrammarTeachExercise`'s
  reveal-a-stage flow, reasoning from `fail()`'s own 200-character-truncated
  error message and a blank-screen screenshot — neither names a file, a
  component, or a line. Adding a `SOAK_FULL_STACK=1` debug flag to
  `scripts/soak.js` (prints the real, untruncated stack from Playwright's
  `pageerror` event) found the actual site on the first live re-run: the
  crash is in `GrammarDrillExercise`, the screen right *after*
  `GrammarTeachExercise` in the same lesson — soak's screenshot, taken once
  the screen had already gone blank, could not distinguish "still on the
  teaching card" from "already past it," and nobody had checked which
  screen actually threw until now.

  Root cause: `GrammarDrillExercise`'s `romanFor` closure read
  `romanOptions![drill.options.indexOf(o)]` — a non-null assertion, not a
  guard — and `shownRoman` called it unconditionally the instant a learner
  picked an answer (`picked` truthy), regardless of `track` or the `roman`
  display flag, because a `const` initializer runs eagerly every render,
  not lazily inside whichever conditional branch of the JSX below actually
  uses it. But `grammarDrillExercise` (`generator.ts`) only ever computed
  `romanOptions` for `track === 'roman'` — every script/`both` track
  exercise carried it `undefined` by design. `showRoman` (the setting
  gating the caption this feeds) defaults `true` for every track except
  literally `'script'` (`useSettingsStore.ts`), and even there a learner
  can flip it back on manually (THE CRITIC's finding, see below) — so
  picking *any* answer on *any* grammarDrill exercise, on the app's own
  default track, crashed unconditionally. Not a rare edge case: the most
  ordinary action in the most ordinary configuration.

  Fixed at both ends:

  1. `generator.ts`'s `grammarDrillExercise` now calls `romanAll` on every
     track, not only `'roman'`. Only the Roman track still drops a drill
     entirely when `romanAll` fails (there the transliteration *is* the
     exercise, per this function's own pre-existing comment); script/`both`
     keep every drill either way, exactly as before this change, now with
     `romanOptions` populated best-effort rather than never.
  2. `GrammarExercises.tsx`'s `romanFor` uses optional chaining instead of
     the assertion, and `shownRoman` only substitutes a value when one is
     actually available, falling back to the un-filled `drill.promptRoman`
     (the same shape the "not yet answered" state already renders) rather
     than crashing — defense in depth for a future concept `romanAll` can't
     handle, since every one of today's 38 real drills already can (checked
     directly, not assumed: `romanAll(d.options)` succeeds for all of
     them).

  A new test (`generator.test.ts`) asserts every real grammarDrill exercise,
  across every real grammar lesson, on the `script`, `both` and `roman`
  tracks alike, has `romanOptions` defined and correctly sized. Confirmed
  it actually catches the regression, not just plausibly related to it:
  reverting `generator.ts` alone and re-running just this test reproduces
  the exact live-observed failure shape (`g-pronouns (both): [...] expected
  undefined to be defined`); restored and reconfirmed clean.

  Live-verified against all three previously-reported reproductions, each
  now 0 failures where all three previously crashed every attempt:
  `--start 29 --seed 7`, `--start 45 --seed 11`, and `--start 200 --track
  roman --seed 55` (the last of these turned out, per THE CRITIC's finding
  below, to not actually be exercising the Roman track at all — still a
  valid `both`-track reproduction of the identical bug, just mislabeled).

  THE CRITIC dispatched (first attempt failed mid-review on a session spend
  limit; redispatched and completed). No BLOCKING. Two MAJOR:

  1. `scripts/soak.js --track roman` is a no-op — `enterAsGuest`
     (`scripts/lib/serve-dist.js`) never writes `track` into the injected
     `harf-settings`, so every soak run ever invoked with `--track roman`,
     including this item's own third reproduction and whichever earlier
     items believed they were exercising the Roman track specifically, was
     actually driving the `both` track under a misleading label. Confirmed
     by THE CRITIC reading `localStorage` back after entry. Does not
     invalidate this item's own fix (re-verified live and via a
     genuinely-reverting unit test, both against the real `both` track
     this bug actually lives on) but is a real, separate defect in shared
     test infrastructure, out of this item's own file scope
     (`GrammarExercises.tsx`) — filed forward as URD-051 rather than folded
     in here.
  2. The new regression test's first version sampled only `['both',
     'roman']`, missing `'script'` — an independently reachable crash path
     since `showRoman` is a learner-toggleable setting, not a permanent
     lock tied to track. Fixed in this same commit: the test now samples
     `['script', 'both', 'roman']`.

  One MINOR, disclosed rather than fixed: when `romanOptions` is genuinely
  undefined (unreachable by any of today's 38 real drills), the fallback
  caption shows the un-filled prompt (literally `"___"`) next to a
  correctly-filled script sentence — not wrong, but not the best possible
  degrade either (hiding the caption once answered would read more
  cleanly). Left as-is: it cannot happen with real content today, and the
  code comment says so.
