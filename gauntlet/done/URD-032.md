## URD-032 — The path's stage-open scroll is a bigger jump than it needs to be, and can go stale mid-session
attempts: 0
files: src/screens/HomeScreen.tsx
definition of done: Two related, non-blocking gaps in URD-002's accordion
  fix, both found in round-2 critique of commit `1344973`:
  (1) Opening a course stage resets scroll to the very top of the page
  (past the greeting, level card, continue card and today's-word card)
  rather than to the accordion itself. DESIGN CRITIC measured this costs
  a real but short scroll back down (~500px, not the ~8000px round trip
  the bug being fixed would have cost) — not disorienting, just not as
  tight as it could be. A middle ground (landing just above the
  accordion, skipping the fixed cards above it) would still guarantee a
  labeled, non-empty state — the collapsed stage list itself is fully
  labeled — while roughly halving the return scroll.
  (2) The mount-time auto-scroll-to-current-lesson (`didAutoScroll` ref,
  fires once per mount) does not re-fire when `currentLevel` advances
  mid-session (e.g. a learner finishes their last lesson in a stage while
  scrolled elsewhere). The accordion itself correctly re-opens the new
  current stage now (URD-002's round-2 fix), but nothing scrolls to reveal
  it if the learner isn't already looking at that part of the screen.
verify: a script driving the real built app confirms (a) opening a stage
  from a scrolled-down position lands within some tighter bound (e.g.
  under 1000px of scroll to reach the newly-open content) than the current
  full-reset, and (b) completing a stage's last lesson mid-session scrolls
  the now-current stage into view without requiring a manual scroll.
notes: Both found and measured (not just theorized) reviewing URD-002's
  round-2 fix — DESIGN CRITIC measured the ~500px vs ~8000px distinction
  directly; THE CRITIC found (2) while checking for effect-ordering risk
  between the accordion's new `currentLevel`-reset effect and the
  pre-existing mount-time auto-scroll. Neither blocked URD-002: the
  current behavior is always labeled and never traps a learner, matching
  the bar both critics graded against. Two precise-positioning approaches
  were already tried and measured wrong against the real react-native-web
  build while fixing URD-002 (documented in HomeScreen.tsx) — whoever
  picks this up should read that history before trying `measureLayout` or
  tracked-`onScroll`-offset again.

  RESOLVED (a): added a `fixedHeaderHeight` ref, captured once via
  `onLayout` on a wrapper `View` around everything above the accordion
  (greeting, level card, continue card, today's-word card, jump-ahead
  hint). `toggleLevel`'s scroll-to-open now targets
  `fixedHeaderHeight.current` instead of `0`. This sidesteps both of the
  previously-failed precise-positioning attempts: no measurement is taken
  AT TOGGLE TIME (the fixed region's height doesn't change when an
  accordion stage collapses or expands, so a once-captured value can't go
  stale the way `measureLayout`'s live query and the tracked-`onScroll`
  offset both did against the real build).

  RESOLVED (b): the existing `useEffect(() => { setOpenLevel(undefined);
  }, [currentLevel])` now also sets `didAutoScroll.current = false` inside
  its body, re-arming the one-shot auto-scroll guard specifically when
  `currentLevel` legitimately advances. `HomeScreen` never remounts
  between lessons, so without this the guard stayed permanently fired
  after its first mount-time fire, and a learner who advanced a stage
  while scrolled elsewhere would see the accordion reopen with nothing
  scrolling it into view.

  Added `scripts/check-home-scroll.js` (new script, wired into
  `package.json` as `check:home-scroll` and into
  `.github/workflows/deploy-preview.yml` right after "the learn path
  doesn't mount the whole course" — `check:all` now reads 28 steps, up
  from 27). It drives the real built bundle, seeds guest progress ~70%
  through the course (matching `check-path.js`'s own scenario, so several
  stages sit collapsed below the open one), scrolls to the bottom, opens
  a collapsed stage, and asserts: scroll lands above 0px (not the
  pre-URD-032 full reset) and under 1500px (a tight landing, not a
  near-full ~8,000px return scroll), and the newly-opened stage's own
  header text is visible near the top of the viewport.

  Confirmed deterministic across 3 repeat runs (539px landing every
  time, against a fixed-header region measuring the same each time).
  Confirmed to fail correctly under induced failure: temporarily
  reverting the scroll target back to `y: 0` and rebuilding reproduced
  "reset scroll to the very top (0px)" exactly, then restored and
  reconfirmed clean.

  Part (b) has NO live end-to-end verification in this session. Its
  correctness rests on code-level reasoning (recorded in `HomeScreen.tsx`'s
  own comment on the effect) about effect ordering and ref-mutation
  timing, not a measurement against the real running app. A full E2E
  path — complete a stage's last lesson mid-session while scrolled away,
  confirm the accordion both reopens and scrolls into view — was
  attempted at length this session and abandoned. The concrete obstacles
  hit, in case whoever picks this up next wants to avoid repeating them:

  - A `meaningPick`/`wordFromMeaning` wrong-answer feedback screen's
    "CONTINUE" control is a plain leaf text node, not `role="button"` —
    its ancestor `Pressable` owns the click handler. Only found via a
    full button-role dump showing zero matches despite "CONTINUE" being
    visibly on screen. Needed a full-DOM leaf-text-node scan instead of a
    `[role="button"]` selector.
  - Distractor/feedback text long enough to wrap to two lines can push a
    bottom "CONTINUE" control below the 900px test viewport, so a
    Y-position heuristic (`y > 780`) is unreliable across different
    random content draws — needed visibility-based detection
    (`offsetParent !== null`, nonzero `getBoundingClientRect()`) instead.
  - `page.locator(...).scrollIntoViewIfNeeded()` hung well past its own
    explicit timeout against a stale, genuinely-hidden element a
    previously-mounted screen (React Navigation keeps some around); root
    cause not fully confirmed. Worked around by dispatching clicks via
    direct `page.evaluate()` DOM queries instead of Playwright locators.
  - Even after fixing all three of the above, the automated playthrough's
    typing-exercise step ("Type this word") repeatedly failed to advance
    past a correct answer in the final observed run, and further
    debugging was not completed.

  Given both critics originally graded (2)'s underlying behavior as
  non-blocking (the accordion still opens correctly; only the scroll-into-
  view step was missing), and the cumulative effort already spent
  automating a full lesson playthrough in this sandboxed browser, further
  E2E debugging was judged disproportionate and stopped here rather than
  continued indefinitely. This is stated plainly rather than glossed
  over, per this project's own instruction to report skipped work as
  plainly as finished work.

  `npx tsc --noEmit`: clean. `npm run format:check`: clean (after a
  Prettier pass on the new script). `npm run check:home-scroll`: passing,
  deterministic.
