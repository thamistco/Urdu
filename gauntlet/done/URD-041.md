## URD-041 — A review's one letter slot always lands on the same position, and so always the same exercise kind
attempts: 0
files: src/exercises/generator.ts
definition of done: `letterExerciseAt(letter, turn, positionIndex)` picks
  `letterTrace` whenever `turn % 3 === 0` and a glyph mask exists — true for
  every glyph sampled. `buildLessonExercises`'s review branch calls
  `letterExerciseAt(l, i, i)` where `i` is the item's index within `refs`
  (due items first, then the interleaved fallback); the fallback's own
  interleave (`fallbackReviewRefs`) always places its first letter at index
  0 of the mixed array. So whenever a review has no letters due (the common
  case from about u14 on, now that URD-017 usually reserves exactly one
  letter slot) that slot lands at `i=0` and is `letterTrace`, every time,
  never `letterForm` or `letterPick`. Measured directly on real generated
  reviews with nothing due: u14 through u39 (26 straight reviews) all draw
  `letterTrace` and only `letterTrace` for their one letter question.
  `letterForm` — the joining-position drill the app is specifically built
  around — never appears in that entire stretch. Vary the position (and so
  the kind) a lone review letter lands on, rather than letting it be
  whatever a fixed loop index happens to produce.
verify: a test that builds several real late-course reviews (u14+) with
  nothing due and asserts the letter exercise kinds drawn are not identical
  across all of them.
notes: Found independently from two angles reviewing URD-017: THE CRITIC
  (MINOR) — "the sole letter exercise lands in the same relative position
  every time, once letterCount is 1" — and CURRICULUM CRITIC (MAJOR,
  curriculum severity) — "the one letter slot late-course is spent entirely
  on tracing, never on the app's own core position-form skill." Same root
  cause (turn/positionIndex tied to a loop index that stopped varying once
  URD-017 shrank the typical letter count to ~1), described from two
  different angles — filed as one item rather than two. Pre-existing
  selection logic (`letterExerciseAt`), made into the dominant outcome
  rather than one of several by URD-017 lowering the letter count that
  used to cycle through positions 0, 2, 4... and so through all three
  kinds. Not blocking — nothing crashes or answers incorrectly, and
  `letterTrace` is itself a legitimate exercise kind, just no longer one of
  three.

  RESOLVED. `reviewIndex` — which review lesson, in path order, this is
  among every review lesson (`ALL_LESSONS.filter(l => l.kind ===
  'review').findIndex(l => l.id === lesson.id)`, floored at 0 for a lesson
  not on the path like `practice-review`) — offsets both `turn` and
  `positionIndex` for a review's letter exercise(s), the same "not a hash"
  technique the pre-existing `turnOffset`/`posOffset` already use for
  letter-teaching lessons (this file has already been burned once by a
  hash that collided on the unlucky pair, documented in that code's own
  comment). Combined additively with `visit` (URD-039's per-completion
  counter, already threaded through this function), so the kind varies
  both across different real reviews *and* across repeat visits to the
  identical review, rather than collapsing to whatever a fixed loop index
  happens to produce.

  Verified directly, not just via the new tests: across all 28 real u14+
  reviews at visit=0, the kind split is now `letterForm: 10, letterPick: 9,
  letterTrace: 9` — a clean three-way rotation replacing the old 26-for-26
  `letterTrace` monoculture — and `letterExerciseAt` is guaranteed to keep
  cycling through all three residues forever, for any future review added
  to the course, since `reviewIndex` is a strict, gapless integer sequence
  (not a probabilistic hash). Replaying one review (`rev-the-wider-world`)
  across visits 0-5 cycles `letterForm → letterPick → letterTrace →
  letterForm → letterPick → letterTrace`.

  New tests in `generator.test.ts`, matching the item's own verify text
  directly: several real late-course reviews draw different kind
  sequences; all three kinds are reachable somewhere across real reviews
  with a letter; the same review rotates across repeat visits too.
  Confirmed the first two catch the exact regression: reverted
  `generator.ts` alone (keeping the new tests), both failed with "expected
  1 to be greater than 1" — the exact single-kind collapse the item names;
  restored and reconfirmed clean.

  CURRICULUM CRITIC found one real MAJOR while checking whether varying
  the kind could ever hit a letter it has no business testing that way:
  `letterForm` is ambiguous for the 13 of 40 `connects: false` letters —
  `isolated`/`initial` and `medial`/`final` are literally identical
  strings for a non-connector (`alif`'s isolated and initial forms are
  both "ا"), so a learner shown one has no way to distinguish it from the
  other and answering the "wrong" one of the pair is marked incorrect.
  Pre-existing (already live in letter-teaching lesson `l-1-2`) and *not*
  introduced by this item — but newly *reachable in review* because of it:
  review's one letter slot could never draw `letterForm` at all before
  this fix (100% `letterTrace`), so review had zero exposure to the
  ambiguity; after it, roughly 4 of 10 real `letterForm` draws across
  late-course reviews hit exactly this pairing. Filed forward as
  **URD-054** rather than fixed here — it touches `letters.ts`'s form
  data model and `LetterExercises.tsx`'s grading, well outside this item's
  own scope of varying which kind gets asked. THE CRITIC independently
  found and confirmed the same gap and concurred with scoping it out.
