## URD-052 — check:theme's legibility floor only sees Tailwind classNames, not inline withAlpha()
attempts: 0
files: scripts/check-theme.js
definition of done: `check:theme`'s `PAPER_FLOOR` rule also catches a
  faded-text colour built with `withAlpha(palette.paper, N)` (or any other
  token) directly in a component's `style` prop, not only a `text-paper/N`
  Tailwind className — both are the same colour on screen, and only one of
  them is currently checked.
verify: with a real component temporarily reading
  `withAlpha(palette.paper, 0.4)` for label text (a real value this repo
  has actually shipped, not a synthetic worst case), `npm run check:theme`
  reports it as a legibility-floor violation. Today it reports clean.
notes: Found by THE CRITIC reviewing URD-036's disabled-button fix
  (src/components/Button.tsx). That fix's first version read
  `withAlpha(palette.paper, 0.4)` for a disabled button's label — composited
  against `palette.ink700`, 3.24:1, exactly the documented worst-case value
  `check:theme`'s own comment cites as the reason `PAPER_FLOOR` (55%) exists
  at all ("57 strings below it... every one of them illegible"). It passed
  `check:theme` anyway, because that check's floor rule pattern-matches the
  Tailwind spelling `text-paper/(\d+)` in file text, and `withAlpha()` is a
  different spelling of the identical colour. Fixed at the call site for
  this one instance (raised to 55%, matching the floor directly rather than
  leaning on WCAG's disabled-control exemption to justify a number this
  project has already measured and rejected once) — but the check itself
  is still blind to the next person who writes the same call differently.
  A green `check:theme` on a file using `withAlpha` for text colour is not
  evidence of anything; this is the same "the comment claims more than the
  code checks" mistake this file's own generator-side sibling elsewhere in
  this repo was written to stop making, now found in a different check.

RESOLVED. `check:theme`'s `PAPER_FLOOR` rule now also scans for
`withAlpha(palette.paper, N)` written inline at a genuine *text*-colour
site — `color:` (a style object's own text colour) or
`placeholderTextColor=` (a `TextInput`'s placeholder, which is text too) —
converting the 0-1 fraction to the same 0-100 percentage `text-paper/N`
already uses, and applying the identical 55% floor.

Deliberately scoped to text-colour props only, not `withAlpha(palette.paper,
…)` wherever it appears: the same faded paper is also a legitimate,
unrelated `borderColor`/`backgroundColor` elsewhere in this app (a disabled
button's border, a step-indicator dot, a drop-zone's dashed outline) — none
of those put paper-coloured text on screen, so none of them are a WCAG
text-contrast question. Verified directly against all 7 real
`withAlpha(palette.paper, …)` call sites in the codebase at the time of
this fix: the new rule flagged exactly the 3 genuine text-colour instances
and correctly left the 4 border/background instances alone (case-sensitive
matching on `color` — `borderColor`/`backgroundColor` are a different
identifier, not a substring of it).

Fixed the 3 real violations this newly caught, raised to the 55% floor:
`LetterLabScreen.tsx`'s position-label caption (0.4 → 0.55) and
`SettingsScreen.tsx`'s two dev-panel placeholder texts (0.3 → 0.55 each).
`npm run check:theme` reports clean on the real repo with these three
fixes applied.

Revert-verified twice: reverting any one of the three real fixes back to
its old value reproduces a `check:theme` failure with the exact predicted
message and line; reverting the check itself (`git stash`) on a
false-positive site (an extreme 5% alpha border) confirmed it still
correctly stays unflagged, proving the text/non-text scoping isn't merely
untested in the passing direction.

**THE CRITIC: no BLOCKING, two MAJOR — both real, both live-reproduced
against the actual repo, both filed forward rather than fixed here.**

1. **Variable indirection.** The regex only sees `withAlpha(palette.paper,
   …)` written *directly* after `color:`/`placeholderTextColor=` — not
   through a local variable, which is `Button.tsx`'s own idiom for every
   other colour it computes (`const text = disabled ?
   withAlpha(palette.paper, 0.55) : TEXT[variant]`, then `style={{ color:
   text }}` several lines later). THE CRITIC set that variable back to the
   file's own documented worst-case value (`0.4`) and confirmed
   `check:theme` reported fully clean; reverted immediately. No live
   regression exists today — `Button.tsx`'s real value is already `0.55` —
   but the exact file whose real bug motivated this item can regress the
   same way again without this check catching it. Filed as **URD-065**.
2. **Multi-line ternary.** The regex's middle segment
   (`[^\n{}]*?`) excludes newlines, so a ternary Prettier wraps across
   several lines evades it entirely. THE CRITIC reformatted the real
   `LetterLabScreen.tsx:159` line (108 characters, single-line only by
   margin against this project's configured 120-character `printWidth`)
   onto its natural multi-line shape with the old `0.4` value and confirmed
   `check:theme` reported clean. Checked directly, not assumed, that the
   naive fix (drop the `\n` exclusion) isn't free: it would let an
   unrelated *sibling* property's own `withAlpha(palette.paper, …)` value
   get misattributed to an earlier `color:` key across a comma — a new
   false-positive class worse than the false negative it would close.
   Filed as **URD-066**, alongside URD-065, since both need either real
   parsing or a materially smarter bound than this regex-based file was
   built to carry (its own header comment already calls it "cheap and
   slightly conservative," not an AST walk).

Both findings are about the check's own claimed scope being wider than
its actual reach, not a live app bug — no real content in the repo
regresses today (confirmed: `grep -rn "withAlpha(palette\.paper" src/`
shows no bare-`color`-variable or wrapped-ternary shape currently in the
tree). The fix's doc comment was rewritten to say precisely what it
catches (the literal-inline case this item's own text named) rather than
the broader claim ("no faded paper text below 55 anywhere") the first
draft made — the same overclaim this item exists to correct, caught one
layer deeper in the fix that corrected it.
