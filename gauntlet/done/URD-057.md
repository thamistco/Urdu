## URD-057 — a subagent's scratch file in src/ or scripts/ silently breaks the next gating run
attempts: 0
files: scripts/check-all.js, scripts/check-*.js (a new one, likely)
definition of done: `npm run lint` globs `src/**/*.{ts,tsx}` and
  `scripts/**/*.js`, and `format:check` globs the same, with no scratch
  exclusion in either `.gitignore` or `.prettierignore`. So any file a
  dispatched critic leaves in those directories becomes a gating failure
  for whoever runs next, attributed to their work rather than to the
  stray file. This has now happened on at least two separate items
  (URD-041's `verify041.js` broke `format:check`; URD-045 accumulated five
  — `scripts/critic-letterspot.js`, `scripts/debug-nav.js`,
  `scripts/debug-lesson0.js`, and two `src/exercises/__scratch_*.test.ts`).
  Fail loudly and by name: list untracked files under `src/` and
  `scripts/` and fail naming them, so the lead is told rather than having
  to hunt through a confusing lint error.
verify: create an untracked file under `src/`, run the check, and watch it
  fail naming that exact path; remove it and watch the check pass.
notes: Found by the OVERSEER reviewing URD-045, alongside a dispatch-prompt
  rule (now in ROLES.md) telling critics not to write there in the first
  place. Both are wanted: the rule reduces the incidence, this makes the
  residue legible. Deliberately do NOT fix this by adding ignore patterns
  to `.prettierignore`/`.gitignore` — a scratch file that silently passes
  the checks is worse than one that breaks them, because it can then sit
  in the tree indefinitely and get committed by an unrelated `git add -A`.

RESOLVED. `scripts/lib/clean-tree.js` exports `strayFiles()`: every
untracked file under `src/` or `scripts/`, via `git status --porcelain
-uall`. Two consumers: `scripts/check-clean-tree.js` (`npm run
check:clean-tree`, standalone, fails naming the files) and
`scripts/check-all.js` (calls the same function as an unconditional early
guard, before the workflow is even parsed, so a stray file fails
immediately and by name rather than surfacing as a confusing `lint`/
`format:check` failure several steps in). `-uall` specifically because
without it `git status --porcelain` collapses a wholly-untracked
directory to one line (`?? src/newdir/`) rather than naming the file
inside it — verified directly, not assumed, by creating an untracked
directory and confirming the actual file inside is what gets named.

Verified against the item's own exact verify text: created an untracked
file under `src/`, ran the check, it failed naming that exact path;
removed it, it passed. Repeated for `scripts/` and for `npm run
check:all` itself (fails immediately, before any real step, not buried in
output). All test files removed and `git status` confirmed clean before
moving on.

Dispatched THE CRITIC via a WIP-commit review (reset after) rather than a
pasted diff.

**THE CRITIC: one real BLOCKING, one real MAJOR (acknowledged, not
fixed), one MINOR (not gating) — all found via direct adversarial testing
against the real script, not reasoning alone.**

**BLOCKING (fixed): `strayFiles()` silently dropped any stray path
containing a space or other character `git status --porcelain` quotes.**
`git status --porcelain -uall` wraps such a path in double quotes with
C-style escaping (`?? "src/my scratch file.ts"`), and the parser's
`startsWith('src/')` check against a line beginning with `"` fails
silently — the exact "Untitled 1.ts"-shaped name an editor or tool
actually defaults to, sailing straight past the guard while still
breaking the real `format:check` glob it exists to get ahead of. THE
CRITIC reproduced this live: `check:clean-tree` reported a false all-clear
while `npm run format:check` correctly flagged the same file. Fixed by
adding `-z` to the `git status` call — NUL-separated output with no
quoting at all, so there is nothing left to unescape. Re-verified against
THE CRITIC's exact repro (a space-containing filename under both `src/`
and `scripts/`) and against the original directory-collapsing case
together — both now correctly named, confirmed by direct testing, not
assumed from the fix's own logic.

**MAJOR (acknowledged via a code comment, not fixed): this check is
`git status`-based and therefore structurally blind to gitignored
files.** Not live today — no existing ignore pattern touches `.ts`/
`.tsx`/`.js` under either directory — but this repo's ESLint config has
no gitignore integration of its own, so a future ignore pattern would
make a file invisible to this guard while `lint` still sees and fails on
it. THE CRITIC confirmed this asymmetry directly: Prettier silently skips
a gitignored file even named explicitly, but `eslint` does not and still
flags it. Disclosed in `clean-tree.js`'s own doc comment rather than
built around, since closing it fully would mean this check re-implementing
`lint`'s own file discovery rather than scanning git's view of the tree.

MINOR, not gating: a transient self-referential message mismatch (this
check correctly names its own two new files as "stray" if run before they
are staged, and the remediation text — "remove it, or move it under the
scratchpad" — reads oddly for that one specific case, since they're the
real feature files, not scratch). Self-resolves the instant they're
staged; not a real defect.

Verified: `npx tsc --noEmit`, `npx vitest run` (259/259, unchanged — no
test-covered app logic touched), `npm run lint`, `npm run format:check`,
`npm run check:clean-tree` (both the original verify text and THE
CRITIC's space/directory/gitignore adversarial cases, tree confirmed
clean after each), and a full `npm run check:all` (30 steps, the new
guard included as an early step) all clean on the final commit.
