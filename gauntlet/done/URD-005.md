## URD-005 — The soak must reach every exercise kind
attempts: 0
files: scripts/soak.js
definition of done: `npm run soak` can be told which exercise kinds a run must
  have exercised, and fails if it finishes without them. Today a run only ever
  reports `tap` and `letterTrace`, because it starts at lesson one and the first
  units are alphabet lessons: `typeWord`, `wordBuild`, `matching`,
  `sentenceBuild`, `grammarDrill`, `dialogue` and `reading` are never reached.
  Seed the guest profile's `completedLessons` so a run can start anywhere on the
  path, and add a flag that asserts the kinds seen.
verify: npm run soak -- --start 90 --lessons 20 --seed 7 --require wordBuild
notes: The soak is only worth its runtime if it visits the parts of the app the
  static checks cannot reason about. Right now it is exercising the two kinds
  that are already best covered.

  Re-reproduced by PLAYER reviewing URD-001 (commit 5301c2f), with a detail
  not previously documented: `soak.js`'s own summary line is actively
  misleading, not just incomplete. "34 lessons, 220 exercises, 0 failures"
  sounds like broad coverage; replaying the identical seed with every
  screen's text logged showed the run never left lesson one — the
  `lessonsPlayed` counter increments on every outer-loop *attempt*, not on
  a completion, so a run stuck retrying after repeated heart loss (see
  URD-006) reports a large, reassuring lesson count while actually
  covering one lesson's worth of content. Reproduced on two independent
  seeds (777001, 55501). Whatever fix lands for this item should also
  make the counter honest — increment on `Lesson complete`, not on entry
  — so its own summary line stops overstating coverage the way the
  original vocab-coverage bug overstated a "23 green checks" pipeline.

  RESOLVED: added `--start <n>` (seeds `completedLessons` from the real
  path via `load()`, so a run can begin anywhere) and `--require
  k1,k2,...` (asserts those kinds were seen, exits 1 with a clear message
  naming what was required vs. seen otherwise). Rewrote exercise-kind
  detection to identify all 15 kinds by fixed on-screen text (previously
  most fell into a generic `'tap'`), added dedicated solvers for
  `sentenceBuild`/`wordBuild` (tile tray) and `matching` (paired taps —
  two real bugs found and fixed here: a candidate y-bound that clipped
  the board's own first row, and a missing `aria-disabled` filter that
  kept re-selecting an already-matched tile forever). Split the
  attempts/completions counters so the summary no longer conflates them,
  while deliberately keeping `--lessons` gating attempts, not
  completions — measured directly that the latter made runtime
  unbounded.

  THE CRITIC's review found and this fix closed a real BLOCKING defect:
  `reading`, `dialogue` and `grammarTeach` could never be named by
  `--require` (dynamic or absent `<Question>` text), so the tool reported
  "never seen" even on runs that had genuinely visited one — and its own
  error text recommended the exact broken invocation. Fixing it surfaced
  that these three screens were not just mislabeled but unreachable:
  `<Button>` (unlike `<Choice>`) never sets `accessibilityRole="button"`,
  so the driver's role-based tap could never find "I've read it," "Got
  it," or "Show examples" at all. Fixed with explicit text-based taps,
  plus a scroll fix (`scrollIntoViewIfNeeded`, then a `page.evaluate`
  scroll for the answer stage) once a longer dialogue pushed those
  controls below the fixed viewport. Also fixed: a lesson that hit its
  step budget (`'ran out'`) never got the same page-reset recovery a
  `'stuck'` lesson does, letting one failure cascade into an unrelated
  second one.

  Chasing that fix surfaced a real, separate app bug — `GrammarTeachExercise`
  throws an uncaught `TypeError` partway through its reveal-a-stage flow,
  blanking the screen, reproduced on two concepts and seeds. Left unfixed
  (it is app code, not this file) and filed as URD-035.

  Also queued as URD-034: the driver's generic answer-tap picks a
  candidate uniformly at random with no attempt at correctness for 7 of
  15 kinds (plus `solveMatching`), so its effective wrong-rate is far
  above the documented 25% — the actual reason no real (non-diagnostic)
  soak run completed a single lesson this session, independent of the
  hearts economy (URD-006). Proven via a throwaway, unshipped `hearts:
  999` patch that isolated answer accuracy as the cause: with hearts
  irrelevant, 10 of 10 real attempts completed cleanly and all four of
  the item's originally-named kinds (`typeWord`, `wordBuild`, `matching`,
  `sentenceBuild`) were seen together in one run — proof the underlying
  logic is correct even though `--require matching` and the item's
  original literal verify command cannot pass against a real run today.
  The shipped verify above was chosen because it is real, reproducible,
  and does not depend on that still-open item.
