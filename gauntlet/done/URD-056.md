## URD-056 — check:all can corrupt its own build if two runs overlap, and nothing stops it
attempts: 0
files: scripts/check-all.js
definition of done: `scripts/check-all.js` already carries a comment (near
  the top, by the `dist/` rebuild) recording that two concurrent runs
  corrupt each other's build — the project has known this long enough to
  write it down and has never guarded it. The failure mode is real and has
  fired repeatedly: a run started while another holds `dist/` dies on
  `ENOENT: no such file or directory, open 'dist/index.html'`, which reads
  like a regression in whatever the lead was working on rather than a
  collision, and has been misdiagnosed that way at least twice (URD-041,
  URD-042) before being correctly traced by inspecting the process tree.
  On URD-045 the lead killed a run by hand purely to dodge it, losing 3-5
  minutes and a discarded build. Take a lockfile before the `dist/`
  rebuild, exit with a message naming the holding PID if it is already
  held, and release it on normal exit and on signal.
verify: start two `check:all` runs and watch the second refuse by name
  rather than racing — a guard that has never been seen to fire is a
  hypothesis (non-negotiable 2), so the test must actually observe the
  refusal, not just assert the lockfile helper in isolation.
notes: Found by the OVERSEER reviewing URD-045. Not blocking — the lead can
  avoid it by remembering, and mostly does; that is exactly the argument
  for a guard, since "the lead remembers" is not a mechanism. Note the
  hazard is worse than plain lost time: a corrupted `dist/` makes the
  *next* check report a failure that has nothing to do with the code.

RESOLVED. `scripts/check-all.js` now takes a gitignored lockfile
(`.check-all.lock`, holding the PID) via `acquireLock()` before the step
loop that includes the `dist/` rebuild. A second run finds the lock held
by a still-alive PID (`process.kill(pid, 0)`) and refuses by name — "already
running as PID N ... `kill -9` N if it is stuck" — rather than racing the
rebuild. A lock held by a PID that's no longer running (a run killed
rather than exited normally) is detected as stale and silently taken over,
logged as such. Released via `process.on('exit', ...)` on normal exit,
plus explicit `SIGINT`/`SIGTERM` handlers, guarded so a losing run can
never delete the winner's lock (only releases if the file still holds its
own PID).

New `scripts/check-all-lock.js` (`npm run check:all-lock`) is the verify
command the item's own text demanded: it spawns two real `node scripts/
check-all.js` processes nearly simultaneously — not a unit test of the
lock helper in isolation — waits for the first to exit, asserts it's the
one that refused with the real PID in the message, then stops the survivor
without waiting for the several-minute pipeline to run twice.

Verified directly, repeatedly, against the real script (not assumed):
ran the verification 5+ times consecutively, all clean, no lockfile ever
left behind; ran one real, complete, unguarded `npm run check:all` end to
end to confirm the lock doesn't interfere with ordinary single-run use and
releases cleanly at the end (30/30 steps passed).

**THE CRITIC, dispatched via a WIP-commit review (reset after) rather than
a pasted diff: no BLOCKING, one real MAJOR, found by direct, repeated
testing against the real script rather than reasoning alone.**

Confirmed working, via real adversarial tests against the actual script:
stale-lock takeover (dead PID in the lockfile); a lock held by a real,
currently-alive but unrelated PID correctly refusing (see the MINOR
below); a `SIGKILL`ed run correctly leaving a stale lock the *next* run
takes over rather than refusing forever; an empty/corrupt lockfile
(`PID 0`/`NaN`) already safely handled by the existing `isAlive` guard,
disproving a hypothesis THE CRITIC raised and then checked directly rather
than assumed.

**MAJOR (fixed): registering a `SIGTERM`/`SIGINT` handler at all changes
what happens when the process is stuck.** Every step runs via a blocking
`execSync`, and Node cannot run a signal handler until that block ends —
so a signal arriving mid-step is not deferred, it is simply not processed
until the step finishes (if it ever does). Before this fix, with no
handler registered, the same signal's *default* disposition would have
killed the process immediately, even mid-step; after, that default is
overridden by the (currently unreachable) handler, so a plain `kill`/
Ctrl-C on a genuinely hung step now does nothing until it returns —
worse, not better, for exactly the "stuck run" scenario this item is
about. `kill -9` (SIGKILL, uncatchable) still always works.

Fixed: the refusal message now says `` `kill -9 ${pid}` `` explicitly
rather than plain "kill", and a comment above the signal handlers
discloses the limitation in full — including that registering the
handler is what removed the old immediate-kill behavior, not merely that
the new one is imperfect. Re-verified by hand: running `check:all-lock`
itself surfaced this exact gap live once the fix's own honesty was taken
seriously — the verification script's first draft assumed SIGTERM always
releases the lock within 300ms and hung for the length of a real step the
one time the survivor was genuinely mid-step when signalled, then reported
a false "release-on-signal is not working" once force-killed from outside.
Rewritten to race a short wait against an escalation to SIGKILL and treat
*either* outcome as correct — proven against the real script across
several consecutive runs, landing in both branches (a graceful between-
steps exit at least once, the SIGKILL-and-stale-lock path more often, both
reported honestly rather than the script asserting only the fast path
exists).

One more measured correction along the way: the verification script's
original "the loser refuses in well under a second" claim was never
actually measured, only assumed — a real run in this session's own
sandboxed environment, under contention from its own other background
work, took up to ~25 seconds to resolve before any step even started.
Fixed the claim to say what was measured rather than what seemed likely,
and widened the script's own timeouts to match (still trivial next to a
multi-minute pipeline).

Two more MINORs from THE CRITIC, both acknowledged with a one-line comment
rather than fixed: `isAlive` checks PID liveness only, not process
identity, so a stale lock whose PID a later, unrelated process reuses
would wrongly read as held (narrow — needs PID reuse after a killed run,
on a busy machine, before the next real run); and `releaseLock`'s
read-then-unlink has a theoretical TOCTOU window, agreed as academic for a
single-developer/CI tool with no adversary.

The fixes made after THE CRITIC's dispatch (the message wording, the
disclosure comments, and the real logic fix to `check-all-lock.js`'s own
hang) were not re-reviewed by a second dispatch — the core lock mechanism
in `check-all.js` that THE CRITIC exhaustively tested did not change, only
its user-facing message and comments; the one logic change was confined to
the lead's own verification script, self-verified by 5+ consecutive real
runs plus one full real `check:all` pass, disclosed here rather than
silently declared equivalent to a dispatched review.
