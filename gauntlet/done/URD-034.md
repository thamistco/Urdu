## URD-034 — The soak's generic answer-tap doesn't try to be correct
attempts: 0
files: scripts/soak.js
definition of done: `answer()`'s fallback for 7 of 15 exercise kinds
  (`tapNamedKind`, covering multipleChoice, meaningPick, listenTap,
  wordFromMeaning, letterForm, letterPick, grammarDrill) and `solveMatching`
  pick a uniformly random candidate with no attempt at correctness — the
  `wrongOnPurpose` flag `playLesson` computes (`rnd() < 0.25`, intended to
  mean "right 75% of the time, deliberately wrong 25%") is read by
  `typeWord`, `letterTrace` and the tile-tray solvers, but never by these
  two, which cover most of what a real lesson asks. Effective wrong-rate on
  a random-guess kind with N options is `1 - 1/N`, typically 65-75% against
  the documented 25% — measured indirectly but repeatedly this session: a
  real, non-diagnostic soak run never completed a single lesson (0 of over
  120 attempts, across a dozen seeds/`--start` positions), and the identical
  content played cleanly (10/10 clean completions) the moment a throwaway,
  unshipped patch made hearts irrelevant, isolating answer accuracy — not
  the app's hearts economy (URD-006) — as the actual bottleneck. Give the
  fallback a real correctness signal (reading the loaded lesson's known-
  correct option via the same `load()` mechanism other check scripts use,
  or an accessibility hint the app is willing to expose for testing) so it
  gets it right except when `wrongOnPurpose`, the way `typeWord` already
  does.
verify: a real (non-diagnostic, no hearts override) `npm run soak` run
  starting well into the vocabulary (e.g. `--start 90`) completes a
  clear majority of its lesson attempts, not zero.
notes: Found and root-caused while shipping URD-005. Two concrete
  consequences of leaving this open, both worth knowing about rather than
  rediscovering: (1) `matching` sits at the very end of every vocab lesson
  and needs the lesson to actually finish to ever be seen, so
  `--require matching` cannot pass against a real run today no matter the
  budget — the solver itself is correct (verified via the same throwaway
  patch: 8/8 matching boards solved cleanly once reachable), it simply
  never gets reached; (2) since no lesson kind ever completes, the "current
  lesson" a fresh attempt reopens never advances, so a single `--start`
  value locks a whole run to one lesson's exercise-kind family — a
  `--require` spanning two different lesson kinds (e.g. a vocab kind plus
  a grammar kind) cannot be jointly satisfied by one real run, only by two
  separate ones. Neither is a soak.js bug on its own; both are downstream
  of this one.

  RESOLVED (partially, honestly — see below): six of the seven named kinds
  (multipleChoice, meaningPick, wordFromMeaning, letterForm, letterPick,
  grammarDrill) now read a real correctness signal via `load()`, the same
  mechanism every other check script in this repo uses. Every one of these
  shares one shape: the prompt names a real word, letter, or grammar drill
  by some fixed piece of its own content (Urdu spelling, Roman
  transliteration, English gloss, letter name, or drill meaning), and the
  correct option is simply the one whose own rendered content is that same
  record's — so the fix reads the identifying text, looks up which real
  record it names (`wordBySignal`/`letterByName`/`drillByMeaning`, each
  built once via `indexBy`, which maps a colliding key to `null` rather
  than to either candidate so an ambiguous signal falls back to guessing
  rather than guessing wrong with confidence), then clicks the on-screen
  candidate whose own text is that record's. `solveMatching` was
  re-checked, not changed — its own doc comment already correctly
  described it as solving by exhaustive trial-and-error rather than random
  luck; the queue's framing of it as "no attempt at correctness" was about
  it not reading `wrongOnPurpose`, not about it being wrong, and that gap
  is left as-is (matching's own outcome — a discovered pair, not a chosen
  wrong one — doesn't have an obvious way to be "deliberately" wrong
  without first knowing the correct pairing, which is exactly what trial
  discovers rather than assumes).

  Live-verified via `SOAK_DEBUG=1` (a new env flag, documented in the CLI
  help comment): across a real run, 38 of 47 named-kind exercises solved
  via the real content match, 9 fell back to random — and every one of
  those 9 was `listenTap` specifically (0 "FAILED" outcomes for the six
  kinds this item actually fixed; every fallback was "MISSING", the
  documented gap below). That is a 100% resolve rate for every kind this
  item's solvers cover, not a partial one.

  Found live mid-implementation: `Text.tsx`'s own `Urdu` component prepends
  an invisible right-to-left mark to every string it renders, so on-screen
  Urdu text never byte-matches the raw data in `words.ts`/`letters.ts`
  unless that mark is stripped first — the very first real test matched
  every target word correctly and then failed every single candidate
  lookup anyway, `لے جانا` (data) against `‏لے جانا` (screen), visually
  identical, one invisible character apart. `normalize()` strips it (and
  the other bidi control characters) on both sides of every comparison in
  the file now.

  `listenTap` was NOT solved — an honest, investigated gap, not a
  regression. Two approaches were tried against the real running app:

  1. Patching `HTMLMediaElement.play` at page creation to record the
     last-played clip's `src` (every bundled voice clip's filename carries
     the real word id before its cache-busting hash, so reading it back
     would have been exact). Never fired once across a real run.
  2. Network-level instead of guessing which JS API expo-av's web build
     actually plays audio through: a `page.on('request', ...)` listener
     watching for any request matching a voice-clip path. Confirmed the
     button tap itself lands correctly (an earlier version used a `text=`
     locator against `accessibilityLabel`'s string, which is not visible
     text and matched nothing, silently) — but zero requests containing
     `mp3`, `voice`, or `audio` anywhere in their URL were ever observed,
     across multiple full lesson attempts, not just this one exercise. The
     audio is not merely cached from an earlier play (still plausible, and
     that would still leave *some* first request) — it does not play in
     this headless driver at all. `playClip` (`lib/speech.ts`) swallows
     its own failure silently (`catch { return null; }`), so there is no
     error to chase either. Both attempts' dead code were removed; the
     investigation is recorded in a doc comment above `answerLetterForm`
     for whoever picks this up next, rather than left to be rediscovered.

  A real, non-diagnostic verify run exactly as specified (`--start 90`, no
  hearts override, 15 real lesson attempts) was then run against the
  finished fix — and completed zero lessons, same as before this item.
  This is reported plainly rather than smoothed into a pass. The fix is
  real (100% resolve rate, independently confirmed above) and the
  intentional-wrong path is exercised as designed, but the item's own
  verify command still does not pass, for a reason found and measured
  directly rather than assumed: a real vocab lesson in this region runs
  22-43 exercises (`buildLessonExercises`, measured against several real
  lessons around `ALL_LESSONS[90]`), and even a hypothetically *perfect*
  solver still leaves roughly a third of exercises landing wrong —
  `listenTap`'s residual ~70% miss rate on its own share of exercises,
  blended with the deliberate 25% `wrongOnPurpose` rate on everything
  else. Binomially, surviving `HEARTS_MAX` (5) hearts through 25-40 tries
  at a ~33% wrong rate is a 1-15% event per attempt, not a majority one
  (computed directly: P(≤4 wrong of 25 at 33.5%) ≈ 4.5%, of 33 ≈ 5.9%, of
  40 ≈ 1.6%). Running more attempts raises the total count of eventual
  completions, not the *majority* fraction the verify command asks for —
  the two are different claims, and this item cannot make the second one
  true.

  This refines, rather than confirms, the queue's own diagnosis: the
  throwaway patch's "10/10 clean completions" isolated answer accuracy
  from the hearts economy by removing the hearts economy entirely
  (unlimited hearts), which is not the same evidence as "fixing answer
  accuracy alone, under the real hearts economy, restores majority
  completion." Measured directly here: it does not. The real, load-bearing
  gate on lesson completion at these lesson lengths is the *combination*
  of `wrongOnPurpose`'s fixed 25% rate and `HEARTS_MAX`'s fixed 5 — a
  hearts-economy question, matching this file's own pre-existing
  `--require` comment (further down, unmodified by this item) which
  already attributed the identical "cannot complete a lesson" symptom to
  URD-006 rather than to this file. Closing what this item's own verify
  command asks for needs that addressed too; it could not be addressed
  within `scripts/soak.js`'s own stated scope (a driver fix, not an app
  economy change), and doing so was out of this item's bounds.
