## URD-045 — A letter's context sighting never asks the learner to find the letter in the word
attempts: 0
files: src/exercises/types.ts, src/exercises/generator.ts, src/exercises/*.tsx
definition of done: URD-020 gave every letter a real-word context sighting,
  but the exercise kinds it can produce (`multipleChoice`/`meaningPick`/
  `listenTap`) are the same whole-word recognition questions used for
  ordinary vocabulary everywhere else in the app — none of them highlight
  or ask about the specific taught letter inside the word. A learner
  answers correctly by picture/meaning matching without ever needing to
  find or name the letter's shape within it, so the sighting shows a letter
  in context without testing that the learner can actually read it there.
  Build a dedicated exercise kind that asks the learner to identify the
  taught letter's position/occurrence inside its context word (e.g. tap
  which tile/segment of the written word is the letter just taught), and
  give it one of the context-sighting slots `LETTER_CONTEXT_WORD`
  (`generator.ts`) already assigns.
verify: a test asserting a letter lesson's context-sighting exercise
  requires identifying the letter's position within the shown word, not
  just its whole-word meaning.
notes: Found by CURRICULUM CRITIC reviewing URD-020. Not blocking — URD-020
  itself offered two designs ("more than one context word per lesson, or a
  dedicated 'spot the letter' exercise kind") and correctly scoped its own
  fix to the first, cheaper one, entirely within `generator.ts`. This is the
  second, bigger design the item named but did not attempt — a new exercise
  kind touches new UI (`src/exercises/*.tsx`), new answerability rules

  RESOLVED. Added a new exercise kind, `letterSpot` (`src/exercises/types.ts`,
  `src/exercises/LetterSpot.tsx`), replacing both `wordExercise(w, poolFor(w),
  track, 'meet', 0)` call sites in the letters-kind lesson branch
  (`generator.ts`'s `letterSpotExercise`/`letterSpotTiles`). The exercise
  shows the assigned context word as one real, correctly-joined line of
  script, then asks the learner to tap which tile of the word is the letter
  just taught — grading the letter (`{id: letter.id, type: 'letter'}`),
  matching `letterForm`/`letterPick`/`letterTrace`'s own convention, not the
  word (a small, deliberate, accepted trade: those ~40 context words each
  lose one incidental "meet"-tier SRS rep from this specific slot, but every
  real word already gets its own dedicated, fully-graded vocabulary-lesson
  exposure via `check:coverage`'s own guarantee, independent of whether it
  doubles as a letter's context word).

  **First design, corrected by CURRICULUM CRITIC before shipping — tiles as
  isolated glyphs.** The first working version split the word into its own
  characters and rendered each as its bare `forms.isolated` glyph — the
  exact shape `letterForm`/`letterPick` already drill in isolation.
  `connector`/`nonConnector` (`data/letters.ts`) show why that's wrong: a
  bare codepoint with no neighbouring character renders isolated by
  construction, so a row of lone codepoints could never show the letter's
  true joined shape — a learner could solve "which tile is X" by
  isolated-glyph matching alone, never reading the word above at all,
  reopening the exact hole this item exists to close. Fixed: each real tile
  now embeds its own true neighbouring character(s), taken directly from the
  word's own text (`letterSpotTiles`) — two real, adjacent codepoints
  rendered as one uninterrupted text run get shaped by the OS's own
  Arabic/Nastaliq engine exactly as they shape in the word itself, the same
  reason `WordBuild.tsx`'s own assembled row reads its tiles as one run
  instead of isolated glyphs. No shaping logic of this component's own is
  needed — it is the same real substring of the same real word.

  **Second CURRICULUM CRITIC finding — no guess floor.** Three of
  `LETTER_CONTEXT_WORD`'s shortest assignments (khe/daal/toe/laam, all
  2-character words) gave a straight 50% guess floor, worse than every other
  recognise-tier letter exercise, which fixes 4 options regardless of
  content. Fixed: pad any word shorter than that floor with decoy tiles
  (drawn from the 40 taught letters' own isolated glyphs, excluded from the
  word's own characters so a decoy can never look like a second right
  answer), spliced into random gaps without disturbing the real tiles' own
  relative reading order.

  **THE CRITIC, one MAJOR — untested runtime grading.** Mutated
  `LetterSpot.tsx`'s inline correctness check to "always true" and confirmed
  directly that nothing anywhere — not the generator tests, not
  `check-answerable.js`, not `check-shape.js` — would catch a learner being
  told "correct" regardless of what they tapped. A real component render
  test is not a cheap fix: confirmed directly that importing anything from
  `LetterSpot.tsx` pulls in real `react-native` view primitives, whose
  Flow-syntax source vitest's own bundler cannot parse at all (every attempt
  fails at parse time, before any test runs) — a genuine, verified
  infrastructure wall, the same one URD-044's `useSessionGradeFlush` was
  built to sidestep. Fixed the same way: extracted the one line that
  decides right from wrong into its own dependency-free module
  (`letterSpotGrading.ts`), gave it a real unit test, and confirmed the
  exact "always true" mutation now fails with the matching shape.
