## URD-060 — six sightings cannot cover four joining forms once two are position-free
attempts: 0
files: src/exercises/generator.ts
definition of done: the four joining forms are this app's central thesis, but
  a letter's `SIGHTINGS_PER_LETTER` (6) sightings now include two that carry
  no position at all — URD-020's `letterSpot` and URD-047's `letterContrast`
  — and of the four that remain, roughly a third render as `letterPick`,
  which also has no position (it asks which glyph makes a sound, with no form
  to show). So the arithmetic does not close: measured after URD-047's
  `nextPos` fix, 4 of 46 letter-slots still never see their `final` form and
  36 of 46 miss at least one of the four. `nextPos` already stopped the
  position cycle SKIPPING a step, which took `final` from 25 of 46 to 4 —
  the residue needs the kind/position interaction changed, not the counter.
  Options: give `letterPick` a position (show the prompt glyph in a form
  rather than isolated), raise `SIGHTINGS_PER_LETTER`, or let the two
  position-free kinds displace a `letterPick` rather than a form-bearing
  sighting.
verify: a test asserting every letter in every real letter lesson is shown
  all four joining forms — the ceiling currently asserted in
  `generator.test.ts` ("`final` reaches all but a handful") tightened to zero.
notes: Found by CURRICULUM CRITIC reviewing URD-047, whose measurement of the
  regression that item caused (14 of 46 missing `final` before, 25 after) is
  what surfaced the older, larger gap underneath it. URD-047 fixed its own
  regression and improved on the pre-existing number; this is the rest.

RESOLVED, taking the "give `letterPick` a position" branch. `letterPick`
(`types.ts`) gained a `position: PositionKey` field; both construction
sites in `generator.ts` (`letterExercise`, `letterExerciseAt`) pass the
same `position` already computed for that call instead of discarding it;
`LetterPickExercise` (`LetterExercises.tsx`) renders every option —
correct answer and distractors alike — at `exercise.position` instead of
always `forms.isolated`. `nextPos`'s own doc comment now explains the
closed guarantee directly: every call now corresponds to a position
actually shown, so any letter with 4 or more calls sees 4 consecutive
integers mod 4, covering all four positions; a letter's worst case is
exactly 4 calls (6 sightings minus `letterSpot` minus `letterContrast`,
when both apply).

`generator.test.ts`'s ceiling test was replaced with a zero-tolerance one:
every letter in every real letter lesson must show all four `POSITIONS`
across its `letterForm`/`letterTrace`/`letterPick` sightings, with no
missing count allowed. Revert-verified: forcing `letterPick`'s position
back to `'isolated'` reproduced 24–36 concrete `lessonId/letterId: missing
X` failures across nearly every real letter lesson (confirmed

**Both critics independently found the same real BLOCKING bug, via two
different empirical methods.** Rendering every `letterPick` option at one
shared position exposes that `distractLetters` (the function building
`letterPick`'s distractor pool) excludes candidates only by sound-token
overlap (`soundsOverlap`) — never by `confusableWith` bucket, never by
rendered-glyph identity. `baRi-ye` and `choti-ye` are each other's own
`confusableWith` partner, share zero reading in common, and render the
byte-identical glyph at both `initial` and `medial` — confirmed directly
against the real letter data (`forms.initial`/`forms.medial` compare
equal; `forms.isolated`/`forms.final` differ). Once `letterPick` can draw
this pair together at `initial` or `medial`, a real generated question
puts two literally identical option tiles on screen, one graded correct
and one wrong, with nothing visible to tell them apart — genuinely
unanswerable, not merely hard. THE CRITIC quantified this via a
258,000-draw Monte Carlo simulation across all 9 real lessons: 900
collisions, ≈0.35% of all `letterPick` draws. CURRICULUM CRITIC quantified
it via 5,000 direct `distractLetters(baRi-ye, 3)` samples: ~7% pulled in
`choti-ye` specifically. Both findings independently re-verified by me
directly (`baRi-ye.forms.initial === choti-ye.forms.initial` and
`.medial` both `true`, `.isolated`/`.final` both `false`) before treating
either as confirmed.

**Fixed**: `distractLetters` gained an optional `position` parameter.
When given, it tracks a `usedGlyphs` set alongside the existing
`usedTokens` set — seeded with the target's own glyph at `position`, and
grown with each distractor's glyph as it's picked — and skips any
candidate whose glyph at `position` is already claimed. This catches
distractor-vs-target collisions and distractor-vs-distractor collisions
alike (the same reason the pre-existing sound-token tracking is built the
same way, per that function's own doc comment), and generalizes past this
one pair: it would catch any future letter pair that happens to share a
glyph at any position, not only the one pair `confusableWith` already
names. Both `letterPick` construction sites now pass their already-computed
`position` through.

Verified the fix directly, not just via the new unit test:
- 20,000 draws of `distractLetters(baRi-ye, 3, 'initial')`: 0 collisions
  (was reproducing the bug moments earlier with the un-fixed function).
- Exhaustive sweep, every real letter × every position × 300 draws each
  (48,000 draws total): 0 glyph collisions anywhere in the option set,
  not just against the one known pair.
- Exhaustive sweep, every real letter × every position × 200 draws each
  (32,000 draws): the fix never starves the distractor pool below the
  required 3 — the exclusion is real but not so aggressive it breaks the
  "always returns n" property the existing tests already relied on.
- Live regression check: reverted only `distractLetters` (kept the new
  `check-answerable.js` assertion below) and re-ran `check-answerable` —
  it immediately failed with `letterPick offers two options with the
  identical glyph at the shown position: fe @ medial: baRi-ye vs
  choti-ye`, a distractor-vs-distractor collision neither critic's example
  named, confirming the general fix (not a special case for one named
  pair) is what's needed and that the new check catches it.

Two unit tests added to `generator.test.ts`'s existing `distractLetters`
describe block, exhaustive over every real letter × every position (not a
sample): one asserting no two options ever share a glyph at the given
position, one asserting the distractor floor still holds once a position

**`scripts/check-answerable.js`'s `letterPick` case gained a

~0.35%-probability event nobody notices. Revert-verified against the

**CURRICULUM CRITIC raised a further MAJOR**: giving `letterPick` a
position removes what looked like "accidental protection" — a letter's
absolute first sighting (round 0) used to always render `isolated`
(hardcoded) even on the rounds where `t === 2` picked `letterPick`, so a
letter's first-ever look was always the stable canonical shape. Now it
can show a non-canonical, position-varying shape on that first look.

**Investigated, not fixed — the premise doesn't hold.** Measured directly
across all 9 real letter lessons which kind each letter's first sighting
actually is, and what position it shows: 12 of 46 letters land their
first sighting on `letterPick` (11 of those now non-`isolated`, this
diff's real effect) — but 19 land on `letterTrace` and 15 on `letterForm`,
both of which already honour `position` and always have (URD-060 didn't
touch either's rendering). Of those 34 pre-existing first sightings, 20
were *already* non-`isolated` before this diff touched anything —
`nextPos` assigns a rotating position to every call regardless of which
kind consumes it, and `letterForm`/`letterTrace` were never special-cased
to stay `isolated` at round 0. So 20 of 46 letters already had a
non-canonical first look; this diff brings the remaining 12 in line with
that existing behaviour rather than introducing a new inconsistency —
there is no "round 0 is always the canonical isolated shape" invariant
anywhere else in the system to have regressed. Building one now (holding
all three kinds to `isolated` at round 0) would be a new feature past this
item's scope, and would cut into the mod-4 coverage guarantee this same
item exists to close for the majority of letters. Recorded here rather
than silently dropped: the concern was reasonable and the measurement
that would have confirmed or falsified it hadn't been done yet when
raised.

**CURRICULUM CRITIC's third finding was architectural, not a defect**: a
preference for the queue item's third named alternative (letting
`letterSpot`/`letterContrast` displace a would-be-`letterPick` sighting,
leaving `letterPick` a pure sound-recognition check with no position
concern at all) over the "give `letterPick` a position" branch actually
taken. No concrete failure was demonstrated for the branch taken — the
coverage math is proven correct by the zero-tolerance test above — so
this is acknowledged as a considered alternative rather than acted on; a
rearchitecture of which kinds occupy which rounds is a materially larger
change than this item's own scope.
