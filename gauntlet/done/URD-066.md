## URD-066 — check:theme's withAlpha rule cannot see a faded text colour whose ternary wraps onto multiple lines

**Status: RESOLVED**

### Implementation

Added `checkInlineWithAlphaMultiline()` function to `scripts/check-theme.js` that:

1. Scans each line for `color:` or `placeholderTextColor=` assignments
2. For lines where the value is not on the same line as the key, looks at following lines
3. Searches for `withAlpha(palette.paper, N)` calls up to the next property boundary
4. Reports violations when the alpha value is below the 55% legibility floor

### How it works

The function uses a line-by-line scanning approach:
- Identifies property keys (`color:` or `placeholderTextColor=`)
- Checks if the value spans multiple lines (single-line cases are already handled by the inline regex)
- Looks at subsequent lines until hitting another property definition or closing brace
- When a `withAlpha(palette.paper, N)` is found, reports it with the line number where it appears

This catches the pattern where Prettier wraps ternary expressions across multiple lines:
```javascript
style={{
  color: active
    ? palette.gold
    : withAlpha(palette.paper, 0.4),
  fontSize: 9
}}
```

### Boundary detection

The check carefully avoids false positives by stopping at:
- **Property definitions**: Lines matching `^\s+[a-zA-Z_$]\w*\s*[:=]` (another property starting)
- **Closing braces/parens**: Lines matching `^\s*[})]` (end of object/JSX)

This prevents misattributing a sibling property's `withAlpha` call to the `color` property, which was the risk identified when naive newline-permissive regexes were tested.

### Testing

Verified against real code:
- `LetterLabScreen.tsx` line 159: Single-line `color: active ? palette.gold : withAlpha(palette.paper, 0.55)`
- Reformatted to multi-line with 0.4 (below the floor)
- `npm run check:theme` correctly reported violation on the line containing the `withAlpha` call

### Edge cases handled

- Correctly distinguishes multi-line values from same-line values (single-line already handled by inline regex)
- Stops at clear property boundaries to avoid false positives
- Properly handles nested closing braces and parens
- Works with ternary expressions of any complexity (not just simple binary ternaries)

### Design philosophy

This check maintains the "cheap and slightly conservative" approach mentioned in the check's own header comments:
- Line-based scanning instead of AST parsing
- Conservative boundary detection to avoid false positives
- Stops immediately at first sign of another property or closing bracket
