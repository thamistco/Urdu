## URD-036 — A disabled button should look disabled, not just say why it is
attempts: 1
files: src/components/Button.tsx
definition of done: `Button`'s disabled state is `opacity: disabled ? 0.4 :
  1` on an otherwise-unchanged fill, border and label — for the `primary`
  variant (warm gold) this stays a shaped, coloured, clearly-tappable-looking
  pill at 40% opacity, not a control that reads as unavailable at a glance.
  Give disabled buttons a visual treatment (desaturating toward a neutral
  tone, a different fill entirely, or similar) that a learner recognizes as
  "will not respond" before they read anything next to it.
verify: DESIGN CRITIC screenshots the same control enabled vs. disabled and
  confirms the disabled state reads as unavailable at a glance, without
  needing the surrounding copy to explain it.
notes: Found by DESIGN CRITIC reviewing URD-006's lockout-screen fix,
  comparing the refill button enabled (gems ≥ 40) against disabled
  (gems < 40) at the same seed: "the only disabled cue is `opacity: disabled
  ? 0.4 : 1` on the whole Pressable — fill, border and label text all dim
  together to a muted orange, still shaped and sized exactly like a live
  CTA... at a glance, before reading, a warm 40%-opacity gold pill still
  reads as 'a button,' just a slightly duller one." URD-006's own fix (a
  subtitle explaining *why* the button won't respond) closes the
  explanation gap but not this one — flagged there as real but out of that
  item's scope, since `Button` is shared across the whole app and changing
  its disabled treatment needs its own review, not a decision folded into
  an unrelated screen's copy fix.

  RESOLVED, across three rounds of finding-and-fixing rather than one clean
  pass — worth recording honestly rather than smoothing into a single
  story, since each round caught something the last one missed.

  **Round 1 (the intended fix).** Replaced the blanket opacity dim with a
  real state change: disabled buttons take on this app's own existing
  inert-and-unavailable fill (`palette.ink700`/`ink800`, the same flat tone
  `HomeScreen.tsx` already gives a locked lesson row's background) instead
  of the variant's own colour, and the 3D raised-pill effect collapses
  (`marginBottom: 0`, the same flat state a button already uses mid-press)
  rather than staying visibly raised. Full opacity throughout — the muted
  tones read as unavailable on their own without needing to fade the label
  too. Verified live against the exact scenario DESIGN CRITIC originally
  found this in (the Out-of-hearts screen's Refill button, gems below vs.
  above the 40-gem cost): a stark, at-a-glance difference between a vivid
  raised gold pill and a flat, dark, muted rectangle.

  **Round 2 (DESIGN CRITIC, dispatched per this item's own verify command).**
  No BLOCKING. One real MAJOR: the fill computation didn't guard `isGhost`
  the way the neighbouring `edge`/`border` computations already did —
  before this item, `fill` was always `FILL[variant]` regardless of
  `disabled`, and `FILL.ghost` is `'transparent'` already, so nothing ever
  showed through; the moment `fill` became disabled-dependent, a disabled
  ghost button started rendering a solid `ink700` box instead of staying
  transparent. Reproduced live on `TracePad.tsx`'s disabled "Clear" button,
  screenshot-indistinguishable from a disabled *primary* button beside it.
  Fixed by guarding `fill` the same way its siblings already were. Two
  MINOR, both disclosed rather than acted on at the time: the disabled
  label's own contrast against `ink700` measured 3.24:1 (below AA's 4.5:1
  floor for normal text, legible in practice, WCAG exempts disabled
  controls); and a code comment overclaiming full parity with
  `HomeScreen`'s locked-row convention (that row also layers `opacity: 0.7`
  on top of `ink700`, which this deliberately doesn't).

  **Round 3 (THE CRITIC, a technical pass on the whole diff).** No
  BLOCKING. Two real MAJOR findings that round 2's own disclosed MINORs
  turned out to undersell:

  1. The `border` computation checked `isGhost` *before* `disabled`
     (`isGhost ? withAlpha(cream, 0.2) : disabled ? ... : palette.ink`),
     so a ghost button's disabled branch was unreachable — its border
     stayed the enabled `withAlpha(cream, 0.2)` regardless of `disabled`.
     Combined with `fill` correctly staying transparent for ghost either
     way, a disabled ghost button had *no visual signal at all* beyond the
     label dimming — the exact "still reads as a button, just duller"
     failure this whole item exists to fix, just relocated onto the ghost
     variant instead of removed. Not an edge case: `variant={x ? 'primary'
     : 'ghost'}` tied to `disabled={!x}` is the standing pattern for a
     "type/select something first" CTA in `SentenceReading.tsx`,
     `WordBuild.tsx` and `RecallExercises.tsx`, so every one of those
     renders exactly this combination for its entire pre-input state.
     Fixed by checking `disabled` first, giving every disabled button —
     ghost or not — the same muted border.
  2. The disabled label's 3.24:1 contrast, round 2's own disclosed MINOR,
     is *exactly* the documented worst-case value `check:theme`'s own
     comment names as the reason its 55%-alpha `PAPER_FLOOR` rule exists at
     all ("57 strings below it... every one of them illegible"). It passed
     `check:theme` anyway only because that check's floor rule
     pattern-matches the Tailwind spelling `text-paper/(\d+)` in file text,
     and this was spelled as an inline `withAlpha()` call instead — a green
     check that wasn't looking at the thing it was supposed to, the exact
     shape CLAUDE.md's non-negotiable #2 names. Fixed by raising to the
     same 55% this project's own check already requires everywhere else,
     rather than resting on WCAG's disabled-control exemption to justify a
     number this codebase had already measured and rejected once.
     `check:theme`'s own blind spot to `withAlpha()` calls is real and
     unfixed — filed forward as URD-052, out of this item's file scope
     (`scripts/check-theme.js`, not `Button.tsx`).

  One MINOR from round 3, fixed in the same pass: `edge`'s own computation
  had no `isGhost` guard either, masked only by an explicit ternary at the
  JSX call site — the same "guard lives in two places, not one" shape that
  let `fill`'s missing guard go unnoticed in round 1. Tidied to compute
  `edge` the same way `fill` now does, and simplified the call site to use
  it directly. One more MINOR, latent and currently unreachable (no caller
  passes `loading` to this shared component today): the loading spinner's
  colour didn't branch on `disabled` the way the label text beside it did.
  Fixed anyway, cheaply, before `loading` is ever wired up for real.

  Verified after all three rounds: `npx tsc --noEmit`, `npm run lint`,
  `npm run format:check`, `npm run check:theme` all clean; `npx vitest run`
  180/180 (unchanged — no test exercises `Button`'s rendering, a real gap
  this repo's testing philosophy doesn't currently have a good answer for,
  since it has no React-component-render test harness set up; verification
  here leaned entirely on real screenshots against the real built app, the
  same "drive the real artifact" principle every check script in this repo
  already uses). Re-screenshotted the ghost-disabled scenario after the
  round-3 fix: `TracePad.tsx`'s Clear (ghost, disabled) and Check (primary,
  disabled) now show the identical muted border treatment, clearly
  distinguishable from either button's own enabled state. Contrast
  recomputed by hand (same WCAG relative-luminance formula, alpha-composited
  against `ink700`): 55% gives 4.74:1, clearing the AA floor the 40% value
  missed at 3.24:1.
