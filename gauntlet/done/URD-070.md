## URD-070 — traceTheLetter's "stroke registered" guard only proves the pointer's first point landed on the pad

**Status: RESOLVED**

### The gap

URD-068 fixed `traceArea()` to read the drawing pad's real `boundingBox()`
instead of inferring one from the caption, and added a guard — after the
walk, assert the "Draw over the grey letter" caption is gone, proving *some*
stroke registered.

THE CRITIC found the guard proves less than it claims: `TracePad`'s
`PanResponder.onPanResponderGrant` (`TracePad.tsx:88-91`) records a stroke and
clears the caption on the bare touch-**down** point alone, before any of the
walk's subsequent `mouse.move()` calls run. So the guard proves only that
`walk[0]` landed inside the pad — not that `walk[1..end]` did. A `traceArea()`
rect that is subtly (not totally) wrong — a small size/scale mismatch, rather
than the total miss URD-068 fixed — could still pass this guard on point one
while later points, especially near the glyph's edges the nearest-neighbour
walk visits, drift off the true pad, producing a partial or garbage stroke
that still "answers" the exercise. "Nothing broke" would not catch this: the
invariant it violates is grading fidelity, not liveness.

### What was tried and rejected

The item's own suggested direction — read back `TracePad`'s "N% of the letter
covered" text after `Check` is tapped, and fail if it's suspiciously low on a
real (non-`wrongOnPurpose`) attempt — was measured directly before being
built, per this project's own rule against assuming a floor. Instrumented
`traceTheLetter` to log the coverage percentage on every genuine full trace
and ran it live:

```
$ SOAK_MEASURE_COVERAGE=1 npm run soak -- --seed 4 --lessons 10
[trace-coverage] 64%
[trace-coverage] 61%
[trace-coverage] 64%
[trace-coverage] 50%
[trace-coverage] 39%
...
n=13  min=39  max=64  mean=60.08
```

A real, correctly-geometried full trace scores anywhere from **39% to 64%**
coverage on this corpus — natural variance from the driver's coarse
nearest-neighbour walk not hugging `scoreTrace`'s thinned skeleton, unrelated
to any bug. A floor tight enough to reliably catch a subtly-wrong rect would
already be failing the healthy app; a floor loose enough not to false-positive
would not reliably separate a real bug from noise either. This route was
abandoned once measured, not assumed to work and shipped.

### The fix

The one place with zero natural noise is the app's own record of what it
drew, not what it scored. `TracePad` renders `strokes` as an SVG `<polyline>`
whose `points` are in the pad's own `0..side` local coordinate space —
independent of grading, independent of how well the stroke happens to score.
`tracedPointsDrift()` reads that polyline back directly off the DOM after the
gesture and checks every recorded point falls inside `[0, side] × [0, side]`
(2px rounding slack). If any point drifted outside, `traceTheLetter` now
calls `fail('trace geometry drift', ...)` with the exact count and surface
size, and returns `false` without ever tapping `Check` — refusing to feed the
app a known-bad gesture rather than letting it be graded.

### Verification

Healthy geometry, unmodified, run twice (once establishing the coverage
baseline above, once confirming zero drift findings):

```
$ npm run soak -- --seed 4 --lessons 8
soak — 0 lessons completed, 8 attempts, 101 exercises answered.
  exercise kinds exercised: letterTrace 23 · letterForm 25 · letterPick 28 ·
  letterSpot 18 · letterContrast 7
  Nothing broke. Seed 4.
```

Zero false positives — the new check adds no noise to a healthy run.

**Broken on purpose, per this project's non-negotiable #2** — reproduced
exactly as the item's own `verify` specified: temporarily scaled
`traceArea()`'s returned rect by 1.18x around its own top-left corner
(correct at the near corner, wrong toward the far edge — a subtly-wrong
rect, not a total miss):

```
$ npm run soak -- --seed 4 --lessons 8   # traceArea() scaled 1.18x, temporarily
  trace geometry drift
    54 of 73 recorded stroke points landed outside the pad's own 348px
    surface — traceArea()'s rect no longer matches the live pad
  trace geometry drift
    165 of 220 recorded stroke points landed outside the pad's own 348px
    surface — traceArea()'s rect no longer matches the live pad
  ...(6 real drift occurrences; each also produced a benign, expected
      "unanswerable screen" as the stuck lesson recovered via reload, so
      the run's 12-failure cap — 6 pairs — stopped it, not 12 drift events)
```

Fires reliably, with a concrete measured count each time, exactly the loud
failure the old guard could not produce. Reverted the repro immediately after
(diffed against a backup to confirm `traceArea()` was restored byte-for-byte).

**Correction, from THE CRITIC's retroactive review**: this repro (~63px off
at the far corner) never tested whether the check's tolerance constant
(`SLACK = 2`) was itself right — it wasn't measured, only picked. Measured
separately (`SOAK_MEASURE_DRIFT_MARGIN`): a real, correctly-geometried walk's
closest point never comes nearer than 30-34px to the pad's true edge, so this
check's real sensitivity floor is that natural margin, not `SLACK` — it
reliably catches a `traceArea()` drift of roughly 30px or more, not the
few-px "subtle" drift the term implies. See `SLACK`'s own comment in
`scripts/soak.js` for the full measurement, and URD-074 (filed forward) for
tightening it further.
